# 世界同步装置 (lh-world-sync)

将一个世界保存为「主世界基准快照」，其它世界一键恢复为它的样子——**设置 + 模组启用状态一起同步**。
适用于「主世界配好一套环境，之后每开一个新团世界都要重新配一遍」的场景。

- 兼容 Foundry VTT **v13**（最低 13.351），**不限游戏系统**——dnd5e、PF2e 或其他系统均可使用（模块只搬运 world 级设置，与具体系统无关）
- 仅 GM 可用；玩家端不加载任何界面
- MIT 授权，可自由分发与修改

## 安装

**方式一（推荐，可检测更新）**：Foundry 设置 →「模组」→「安装模组」→ 在底部粘贴以下地址：

```
https://raw.githubusercontent.com/Ryuka16/lh-world-sync/main/module.json
```

**方式二（手动）**：从 [Releases](https://github.com/Ryuka16/lh-world-sync/releases) 下载 `lh-world-sync.zip`，解压出的 `lh-world-sync` 文件夹放入 `Data/modules/`，重启 Foundry 后在模组管理中启用。

安装后在控制台输入 `window.__WSYNC_VER` 可确认加载的版本号。

## 功能

| 功能 | 说明 |
|---|---|
| 存主世界 | 将当前世界的全部 **world 级设置**（各游戏系统与各模块的设置）保存为快照，存于模块 `storage/` 目录，服务器上所有世界共享读取 |
| 恢复主世界 | 将当前世界恢复为基准快照的状态：设置与**模组启用状态**一并恢复，完成后页面自动刷新 |
| 自动提醒 | GM 进入世界时若发现有差异，自动弹窗询问：**恢复主世界 / 暂不恢复 / 不再自动提醒**（可随时改回） |
| 查看差异 | 恢复前列出差异清单：每一项显示「当前值 → 基准值」，并标注 **→开启 / →关闭 / →修改**。超过 120 项时，完整差异键会输出到浏览器控制台（F12 → Console，搜 lh-world-sync） |
| 回档 | 每次恢复前自动记账，回档＝按账本精确还原上一次恢复改动的设置；此后手动调整的其他设置不受影响。**每个世界一个账本文件**（`apply-log-<世界ID>.json`），各留各的、互不干扰；已回档过的记录会被标注，恢复之后又被改过的设置会一并提示。回档过程中若出错会自动还原到回档前的样子，不会停在半路 |
| 快照文件 | **导出下载 / 复制全文 / 从文件导入 / 粘贴导入**。⚠ 导出的内容是**当前世界的实时设置**（用于备份或搬到别的服务器），不是服务器上那份主快照；要主快照本身请在服务器上取 `storage/world-snapshot-master.json`。导入时二选一：**设为主快照**（跨服务器迁移用，会覆盖服务器上的主快照）或**仅恢复本世界**（自己留底、临时回滚用） |
| 恢复范围 | 「高级选项」中可按模块勾选恢复范围，点**保存范围**后成为这个世界的长期偏好——手动恢复与进世界自动提醒都按它执行（默认全部恢复） |
| 主题 | 深空蓝 / 蓝白 / 琉璃绿 / 鎏金 / 薄荷 五种配色，每位用户可自行选择（client 级设置） |

## 入口

- 右侧边栏「设置」齿轮旁的图标按钮（🔄 样式，悬停显示「世界同步装置」；该按钮只有图标没有文字）
- 设置 → 模组设置 → 世界同步装置 → 「世界同步装置面板」
- 控制台：`window.lhWorldSync.openPanel()`

## 典型用法

1. 在一个配置齐全的世界（基准团）中打开面板，点击 **存主世界**
2. 进入任意其它世界 → 启用本模块 → GM 进入时会弹窗提示差异 → 点击 **恢复主世界** → 页面自动刷新，设置与模组启用状态全部到位
3. 若结果不符合预期 → 在面板中点击 **回档**，还原到恢复前的状态并查看清单
4. 跨服务器迁移 → 在「高级选项 → 快照文件」中导出**当前世界的设置**文件，在目标服务器上导入并选 **设为主快照**，此后该服务器的所有世界都以它为准

> 面板默认只显示「存主世界 / 恢复主世界 / 回档」三个按钮与一行状态；恢复范围细调、快照文件、自动提醒开关均收在「高级选项」折叠区中。

## 快照格式 (schema 1)

```json
{
  "schema": 1,
  "app": "lh-world-sync",
  "appVersion": "1.3.0",
  "sourceWorld": "主世界名",
  "savedAt": "ISO 时间",
  "systemId": "dnd5e",
  "systemVersion": "5.3.3",
  "coreVersion": "13.351",
  "modules": { "midi-qol": "13.0.55", "...": "..." },
  "settings": [ { "key": "dnd5e.largerTokenArms", "value": true }, "..." ]
}
```

## 回档账本格式 (schema 2)

回档记录与快照同目录，**每个世界一个文件**：`apply-log-<worldId>.json`（`worldId` = `game.world.id`，世界改名不影响归属）。文件里只会有本世界那一格：

```json
{
  "schema": 2,
  "worlds": {
    "<worldId>": {
      "ts": "ISO 时间",
      "worldId": "<worldId>",
      "worldTitle": "世界显示名",
      "appVersion": "1.3.0",
      "status": "pending",
      "rolledBackAt": null,
      "after": { "<设置键>": "…本次恢复写入的值…" },
      "prev": { "<设置键>": { "present": true, "value": "…恢复前的值…" } }
    }
  }
}
```

- `worldId` 取 `game.world.id`，世界改名不影响归属
- `prev` 只记录「上一次恢复实际改动过的键」；`present: false` 表示该键当时并不存在（回档时把它删掉）
- `after` = 本次恢复**写入的值**，用于回档前发现「恢复之后又被人工改过」的设置并给出提示
- `status`：`pending`（未回档）/ `rolled-back`（已回档过一次，再点回档会二次提示）+ `rolledBackAt` 时间
- 回档只认自己那个账本文件：读不到就提示「暂无可回档记录」，**绝不会拿别的世界的旧值回填**
- **v1.1.0 及更早的旧文件 `apply-log.json`（所有世界挤在一个文件里）只读不写、不会被删除**：若本世界条目只存在于旧文件里，仍能被读到并用于回档；下次恢复起会写进新的 `apply-log-<世界ID>.json`。确认迁移无误后，可在服务器上手动删除旧文件

## 边界与安全（设计决策）

- **同步范围为 world 级设置**；client 级设置（浏览器本地偏好）与 **user 级设置**（模组给每个玩家单独存的那份偏好）都不在同步范围内。**不同步世界文档**（角色、场景、物品、日志、用户等）——本模块只搬运 `game.settings.storage.get("world")` 里的设置。注意两点：① Foundry 的**用户（User）属于世界数据**，每个世界有自己的一套玩家与权限，换世界就是另一份名单（出处：`client/documents/collections/users.mjs:21` `class Users extends WorldCollection`）；② **user 级设置与 world 级设置存在同一个集合里**（出处：`client/helpers/client-settings.mjs:44-46` 把 USER scope 指向 world 集合），本模块按 `doc.user` 非空跳过它们，所以玩家个人的开关不会跟着同步。
- **默认排除** `core.time`（世界时间）、`core.permissions`（权限，GM 专用）与 `foundry-mcp-bridge.lastActivity`（该模组的心跳时间戳，每次刷新都会变化，同步无意义且会造成误报差异）；面板「高级选项」中可追加排除项。
- **模组启用状态**（`core.moduleConfiguration`）默认包含在恢复范围内：此前被关闭的模组会随主世界重新启用。恢复后页面自动刷新，无需手动操作。注意这是**整体覆盖**——本世界独有的开关状态会被主快照里那一份替换掉。唯一例外：**本模块自己会被强制保留为启用**（否则一旦主快照来自没装本模块的世界，恢复后你连面板入口都找不到）。
- **恢复前先记账、失败尽力回滚**：批量写入抛错时会按账本还原；如果连还原本身也失败（权限被拒 / 网络中断 / 页面被关掉），弹窗会**明确告诉你「没还原成功、请勿刷新页面」**，而不是用一句「已自动回滚」把风险盖过去。**回档同样有失败还原**，并且报告会把「真的动过的项」与「本来就不存在、什么都没做的项」分开报数。
- **覆盖主快照前先备份上一份**：点「存主世界」或导入时选「设为主快照」，都会先把服务器上现有的主快照原样另存为 `world-snapshot-master.prev.json`。⚠ 这个备份是**固定名、只保留最近一代**——连续两次覆盖之后，最早那份就没有副本了。因此「存主世界」另加了一道**内容体检**：当前世界的设置数不足 20 项、或骤降到服务器主快照的三成以下时，先警告并要求再点一次才算确认；一项都没有时直接拒绝。真正可靠的长期退路是**把快照文件导出到自己电脑留底**——服务器上不会保留多代主快照（主快照动辄 8MB 以上，而 Foundry 没有游戏内文件重命名 API，多代轮转的读写代价不可接受）。
- **恢复完成后 10 秒自动刷新页面**（模组启用状态需刷新页面才生效）；弹窗里可点「立即刷新」，也可以点「稍后再刷新」取消自动刷新。这次改动的清单会存进浏览器会话，刷新后仍可在面板里点开「上一次恢复改动了什么」。如需撤销，刷新完成后点击「回档」即可。
- **Foundry 未提供游戏内文件删除 API**：快照与账本均为固定文件名覆盖写入（主快照 `world-snapshot-master.json`、主快照备份 `world-snapshot-master.prev.json`、账本 `apply-log-<世界ID>.json`、账本上一代备份 `apply-log-<世界ID>.prev.json`、操作锁 `operation-lock.json`；账本内容读不懂时会先原样另存 `apply-log-<世界ID>.bak-<内容指纹>.json`，同一份内容只备一次），不会累积文件。注意：**本模块不删任何文件**——v1.1.0 及更早的合并账本 `apply-log.json` 会原样保留（只读兼容），确认不需要后由你在服务器 `Data/modules/lh-world-sync/storage/` 中手动删除。
- **这些文件在服务器上是「可被直接下载」的，请注意暴露范围**：快照、账本与锁都放在 `Data/modules/lh-world-sync/storage/` 下，而 Foundry 会把整个 `Data/` 目录作为静态资源直接提供（出处：`dist/server/express.mjs` 中 `express.static(paths.data)`），前面**没有任何登录校验**——也就是说，任何人只要知道地址，无需登录即可下载这些文件，而它们包含你世界的**全部 world 级设置值**（其中可能有模组存放的 API key 之类的敏感配置）。这是 Foundry 的通用行为、不是本模块造成的，但本模块会把配置汇总成一份文件放在那里，所以请按自己服务器的暴露范围自行评估；不需要留底时，直接删除 `storage/` 下的文件即可（本模块不删任何文件）。
- **并发保护**：两个 GM 同时做世界同步操作（恢复 / 存主世界 / 回档 / 导入设为主快照）时，后一个会被拒绝并提示；同一个浏览器会话里的重复点击也会被挡住（文件锁对同一会话是放行的，所以另加了一道会话内的闸）。锁里同时记录了**会话标识**与**页面标识**：如果你在操作进行中刷新了页面，新页面不会把上一个页面的锁当成自己的——它会明确提示「你刚刷新过，上一次操作可能还在跑」，而不是放行（这是 v1.2.8 修掉的一条会丢失撤销点的路）。锁写在 `storage/operation-lock.json`，**约 2 分钟**未释放自动失效（持有者崩溃也不会死锁）。⚠ 文件锁不是原子操作，属尽力而为，不适合多人高频同时恢复的场景。
- **快照校验**：导入时校验 `app` / `schema` / 键类型 / **value 字段是否存在** / 重复键 / 条目数上限 / `modules` 结构，非法文件直接拒绝；系统版本、Foundry 版本、缺失模组只作**提示**（列出差异后由你决定是否继续）。恢复时**会跳过本机未安装模组的设置键**（避免产生没人读、却会随快照在服务器之间复制的悬空键）。
- **写入口守卫**：所有写操作（恢复、回档、写入主快照）执行前统一检查 GM 身份，`window.lhWorldSync` 接口同样受限。

### v1.3.0 变更

本版把第七轮整体盲审剩下的 13 项一次收口（此前每版只改 5~10 项）：

- **导入文件体积上限**：超过 32 MB 直接拒绝，不再读进内存（一份几百 MB 的 json 会让浏览器卡死，而原来的校验在读之后）。
- **拒收含「始终排除键」的快照**：`core.time` / `core.permissions` / `foundry-mcp-bridge.lastActivity` 恒定不同步，外来快照带着它们会被拒绝导入（本模块产出的快照不含这些键）。
- **没有稳定世界标识时拒绝写账本**：取不到 `game.world.id` 时不再退回世界标题当文件名 —— 两个同名世界会互相挤掉对方的撤销点。此时操作中止、世界零改动。
- **回滚按「本次真正创建的文档 id」删除**：原来靠反查，刚创建的文档在集合缓存里可能还查不到，落空会把新文档留在世界里，成为同 key 的第二份设置。
- **网络读取加 30 秒超时**：服务器「连上但不回包」时不再无限等待（面板停在读取中，用户只能刷新页面 —— 而刷新正是历史上出事的入口）。
- **自动刷新前检查是否有操作在跑**：恢复还在写的时候不再自动刷新页面。
- **复制到剪贴板改为可失败**：`copyPlainText` 的 Promise 现在会 await，被浏览器拒绝时提示真实原因，不再显示「已复制」却复制不到。
- **导出 / 复制的口径写清楚了**：导出的始终是**当前世界的实时设置**，不是服务器上那份主快照（原来按钮只写「导出快照」，容易被理解成导出基准）。
- **差异清单超过 120 项时的出口改了**：原来指向「导出快照」（导的是设置值，对不出差异），现在把完整差异键输出到浏览器控制台。
- **性能**：当前世界键值加了 2 秒短时缓存（原来每勾一下都要重新遍历 1435 项）；不可用项去重由 O(n²) 改为 Set。
- **玩家端**：控制台上不再暴露写操作入口（面板仍可打开查看）；自动提醒开关对玩家隐藏。

### v1.2.9 变更

本轮**不改功能行为**，只收掉两处结构病（第八轮整体盲审点名的四类「同一事实存多份副本」中先拆的两类）：

- **「哪个文件读失败了」不再由一个全局变量承载**：原来读锁文件、主快照、账本、旧账本共用一个 `storageLastError`，后一次读会覆盖前一次，于是「刚读完 404、下一句又读到 5xx」这类交错会让提示说错原因 —— 而它正是好几条错误提示的判据。现在每次读取的失败原因随结果一起返回（`{ text, error }`），404（确实不存在）与「真出错」（5xx / 断网）在源头就分开。
- **操作互斥统一成一个入口**：原来恢复、回档、存快照各写一套「拿闸 + 拿锁 + 释放」的代码，三套的返回值形状还不一样（这正是「改一处漏两处」的温床）。现在统一走 `withOpLock`，提示语里会带上具体操作名（如「已有进行中的『恢复主世界』操作」）。控制台入口 `window.lhWorldSync.rollback()` 不再自己拿闸 —— 原来会与内部闸冲突，变成「自己把自己挡住」。

同步更新了 4 条测试断言（返回值形状与提示文案变化），逐条判定为预期变更。

### v1.2.8 变更

这一版来自一次换了打法的审查：三个**互不通气**的独立审阅者（一个从零冷读全文、一个先只读文档再去核对实现、一个专门模拟刷新／断网／双标签页／畸形文件来破坏它）各自通读代码，而且**都没有拿到我已知的问题清单**（给了清单就只会看到清单上的东西）。它们独立地落在同一个结论上：这个模块的问题不在某个函数写错，而在**同一类事实被存了多份副本**——「上次读取是不是失败」有 5 个变量在记、「操作互斥」有 3 套实现、「哪些设置该写」有 4 套判据、「失败后怎么还原」有 2 处几乎逐字重复。这才是六轮修下来反复出现「修了一半」的真正原因。

本版先修**会造成永久损失**的几条（把多份副本合并成一份的结构性改动放在 v1.2.9）：

- **修掉一条「恢复途中按 F5」会让撤销点消失的路**（本轮最危险的一条）：恢复跑起来后，如果中途按了 F5，会话闸（存在内存里，刷新必然清零）与文件锁（存在浏览器会话里，刷新必然还在）**两道防并发在同一个动作上同时失效**。于是新页面可以立刻再点一次恢复，两次恢复同时写设置、同时写账本，后写的那次把账本整格覆盖 —— 唯一能「回到恢复前」的记录就此永久消失，世界还可能停在一个从未存在过的中间状态，而界面全程没有任何提示。
  现在把「同一浏览器会话」再细分成「同一页面」：锁里记下当前页面的标记，只有会话号与页面标记都相同才算自己的锁。刷新后再点恢复，会明确告诉你「检测到你刚刷新过，上一次的恢复可能还在跑，请等它结束」—— 既不会默默放行，也不会含糊地说成「另一位 GM 正在操作」。
- **账本覆盖前先留一代**：即使上面那道防线真的被绕过，覆盖之前也会先把上一份账本另存为 `apply-log-<世界ID>.prev.json`。防并发不能全押在锁上 —— 文件锁是「尽力而为」的，这句写在代码注释里，过去没有兑现到数据上。
- **「存主世界」加了内容体检**：当前世界的设置数不足 20 项、或骤降到服务器主快照的三成以下时，先警告并要求**再点一次**才真的覆盖；一项都没有时直接拒绝。原来的风险是：完整主快照 → 切到一个空世界再点一次存 → 备份只保留一代 → 再存一次，完整快照在服务器上再也没有副本。
- **恢复完成会记账**（账本状态写 `applied`）：原来写完设置就结束，账本一直停在「还没回档过」。如果恢复中途崩掉，世界停在半成品，几天后再点回档，界面会把「上一次没写完」解释成「你后来又改过」—— 编出一个看起来合理、却完全错误的原因。现在停在半成品时不再报这种假漂移。
- **会话闸会自愈**：上一次操作异常中断后，超过 5 分钟自动判定为已中断并放行。原来会一直回答「请等它完成」，把用户永久关在门外，只有刷新页面能救 —— 而刷新又恰好是上面那个坑的触发器。

### v1.2.7 变更

上一版（v1.2.6）修过的那些地方，又经一轮独立审阅复核，发现 7 处没修干净、或修出了新问题，已全部修掉：

- **存主世界后不再把刚上传的快照整份读回来**：快照在实测环境里是 8.8MB。「存主世界」写完文件后，原来紧接着为了刷新状态栏那一行差异数，又把整份快照下载 + 解析一遍（本机实测下载约 4 秒）。现在直接用刚生成的那份数据刷新，省掉这趟往返 —— 世界越大、存档越慢，感知越明显。
- **回档入口不再把「读失败」说成「没有记录」**：上一版给「旧版合并账本读取失败」单独记了状态，但**回档的说明弹窗没读它** —— 主账本本来就不存在、旧账本又读不到时，界面说「本世界暂无可回档记录」，而撤销点很可能就躺在那一份读不到的文件里。（真正执行回档的逻辑上一版已修对，只有这个弹窗漏了。）
- **账本坏了要说清楚**：账本文件存在但内容读不懂时，界面原来也说「暂无可回档记录」，坏在哪、另存成了什么只在控制台。现在直接显示原因，并告诉你原文件被另存成了哪个名字 —— 可以去服务器上看它是否还留着你要的撤销点。
- **坏账本的备份不再每次读取都多一个**：另存文件名从时间戳改为内容指纹 —— 同一份内容只备一次（原来每打开一次面板就会多出一个 `.bak-<时间戳>.json`）。
- **账本内容补上硬校验**：原来只检查 `schema` / `worlds` 两层结构，账本内容不对时（例如某条记录不是对象）回档会照着账本里的键去**删、去写真实设置** —— 快照侧有十几条硬校验，账本侧一条都没有。现在逐条校验：键名必须含点、每条记录必须是对象、`present` 必须是布尔值、条目有上限。
- **解析失败不再留旧基准**：状态栏的差异数取自缓存的主快照；当快照文件损坏 / 解析失败时，上一版只是报个错，旧快照仍留在缓存里，下一次刷新会拿**旧基准**算差异、还显示得好好的。现在解析失败即清空缓存。
- **保存「不参与恢复的设置」后刷新状态栏**：排除表改了，状态栏那行差异数原来没跟着重算（「保存范围」有这一步，它漏了）。

### v1.2.6 变更
- **修掉一处会让恢复永久失败的错误归因**：v1.2.5 把「旧版合并账本 `apply-log.json` **读取失败**」也算进了「账本不可写」的判据，而那份文件是**只读**的（本模块从不写它）。结果是：服务器对这份永远不会被写的文件持续报错时，**你的每一次恢复都会被中止**，提示还写着「为避免覆盖本世界原有的回档记录」——这个理由对一份不会被写的文件不成立。现在旧账本读失败只影响「回档记录能不能查到」，不阻断恢复。
- **回档不再允许用过期账本**：主账本读取失败、却从旧账本里凑出了条目时，v1.2.5 会照常回档 —— 那是在用可能已经过期的旧值覆盖世界，还会把主账本里更新的那条标记成「已回档」。现在与写入路径规则一致：主账本读失败一律拒绝回档，并说清是读失败而不是「没有记录」。
- **「N 项因缺模组没恢复」的数字终于准了**：以前拿**整份快照**统计，既不看你勾了哪些模块，也不扣掉你自己排除的键——只勾一个模块也会报「另有 250 项未恢复」，还把 `core.time` 这类故意永不恢复的键算了进去。现在统一口径：不在排除表 + 模组确实没装 + 在本次勾选范围内。
- **「基准一致」不再掩盖没落地的项**：跨服务器搬家时，差异可能全在没装的那几个模组上。以前面板、差异弹窗、进世界自动提醒一律说「一致」，你会以为已经恢复完了；现在会明确告诉你「另有 N 项没有恢复，因为本世界没装对应的模组」——面板状态栏、恢复报告、事后回看清单里都能看到。
- **面板勾选列表标出装不了的模组**：本机没安装的模组以前显示成可勾选，勾了却不生效（UI 承诺与行为不符）。现在整行标灰并写明「本机未安装这个模组 · 本次不会恢复」。
- **修掉「面板不再读两次快照」的反噬**：主快照解析失败（文件损坏 / 结构不符 / 条目超限）时，状态栏会沿用上一次打开面板时的旧基准算差异、还显示得好好的；现在解析失败即清缓存并如实报错。
- **兜底补齐**：账本格式不符时**先另存一份**再新建（避免将来升级结构时静默丢记录）；「已回档过一次」的标记失败时会留日志（不再无声失效）；「另有 N 项没恢复」进入恢复报告与事后回看清单（原来只活在一条刷新就消失的通知里）；释放文件锁与会话闸的顺序调正（避免同一标签页的下一个操作被上一个的收尾动作误删锁）。

第四轮：请独立审阅者**专门审 v1.2.4 那次修复本身**（15 条声明里 12 条修好、2 条只修一半、1 条引入新问题）。这一轮抓到的头号问题是致命的，且完全由 v1.2.4 引入：

第三轮：两份**独立盲审**（审阅者看不到作者的判断，只给代码与检查清单）通读全文后的汇总修复。它们的价值恰在于「作者视角 ≠ 审阅者视角」——其中两条是 v1.2.1 / v1.2.2 声称修过、实际只修了一半的路径：

- **账本被覆盖前先自保**：账本是「回档」的唯一依据，服务器上没有它的备份。现在读账本失败时**拒绝执行恢复**（世界一个设置都不会动），而不是照旧覆盖写一份新账本把旧记录挤掉

- **锁的假拒绝修掉**：写锁后回读失败时（`JSON.parse(null)` 不抛错），自己刚写的锁会被判成「别人的锁」，用户看到「已有进行中的操作（另一位 GM）」——而根本没有人持锁。现在只有读到「明确的、不是自己的」锁才拒绝

- **导入更严 / 落点更干净**：快照条目缺 `value` 字段直接拒收（否则会写入失败，或被序列化丢掉后变成「报告说成功、实际没改」的假成功）；恢复时跳过本机未安装模组的键
- **界面对得上行为**：面板「进入世界时自动提醒」复选框按真实设置值显示（以前在「还没存过快照」时恒显示未勾选，而默认其实是开）；「不参与恢复的设置」写明三项默认排除无法移除、并念出实际生效的并集（以前删掉默认项也提示「已保存」）；主快照被导入替换后面板状态栏立即刷新；读取主快照失败不再无声无息
- **健壮性**：读取响应体失败不再抛出到无人接管的地方（以前表现为「点了没反应」）；补上差异箭头 `.wsync-v-arrow` 的样式；删掉一段永不执行的死代码
